# 근로고래 보안 — "1인 다계정(Sybil)" 리스크 보고서

- 날짜: 2026-07-11
- 대상: 회원가입·회원탈퇴 재가입 쿨다운의 **신원(identity) 전제**
- 배경: 회원탈퇴 재가입 쿨다운(30일·이메일 해시) 검토 중, "이메일 별칭으로 우회되면 보안 이슈 아니냐"에서 출발 — **구글 메일에 국한되지 않는 일반 문제**로 확장.
- 관련: 현수 `docs/보안점검-2026-07-10.md`(M3 학교검증·M4 열거·H2/H3 광고 경제) · 별칭 세부 메모(`project-todo-email-alias-abuse`)

## 핵심 명제

**"이메일 = 사람"이라는 전제가 거짓이다.** 재가입 쿨다운은 *"탈퇴 → 같은 이메일 즉시 재가입"* 만 막는 **좁은 방어**이고, 한 사람이 **여러 이메일/별칭으로 여러 계정(Sybil)** 을 만드는 것은 못 막는다. 이건 Gmail의 별칭 트릭에 국한된 게 아니라 **여러 경로**로 성립한다. 그리고 우리 앱은 "1계정 = 1사람" 가정에 **광고 경제**와 **리뷰 무결성**이 걸려 있어 실제 피해로 이어진다.

---

## 다계정 생성 벡터 (구글 아니어도)

| # | 벡터 | provider 의존 | 비고 |
|---|------|---------------|------|
| V1 | **`+` 서브어드레싱** `you+w1@` | 일부(Gmail·O365·iCloud·Fastmail 등 O / 네이버 등 X) | 표시 남음 |
| V2 | **Gmail dot 무시** `y.o.u@`=`you@` | 구글 전용 | ⭐ 흔적 안 남 |
| V3 | **캐치올(catch-all) 도메인** `anything@univ.ac.kr` | **무관(도메인 설정)** | ⭐⭐ 제일 강력 — 무한 계정, 한 함으로 수신. 일부 학교/랩 도메인이 이럴 수 있음 |
| V4 | **복수 실제 이메일** | 무관 | 편입·복수전공·대학원·동문·랩 공용·지인 메일 — **트릭 없이** 여러 `*.ac.kr` 보유 |
| V5 | **서브도메인** `user@dept.univ.ac.kr` | 무관 | 둘 다 `.ac.kr` 통과, 다른 문자열 |
| V6 | **쿨다운 30일 만료** | — | 같은 이메일도 30일 뒤 재사용 → 시간축 반복(부차적) |

> 대소문자·앞뒤 공백은 우리가 `lower(trim())`으로 이미 중화 — 양호. **핵심 구멍은 V3(캐치올)·V4(복수 실메일)로, 이메일 정규화로도 못 막는다.**

## 우리 방어의 현 위치

- **재가입 쿨다운(이메일 해시):** V1·V2는 정규화로 막을 수 있으나 현재 미적용. V3·V4·V5는 **원천적으로 못 막음**(다른 이메일이니까). V6만 지연.
- **`*.ac.kr` 게이트 + OTP 인증:** 문턱은 올리지만(수신 가능한 학교메일 필요) 위 벡터엔 무력.
- **학교 소속 미검증(현수 M3):** 아무 `.ac.kr`로 임의 학교 주장 가능 → 다계정과 결합 시 리뷰 신뢰 훼손 가중.

## 영향 평가 (뭐가 실제로 깨지나)

1. **광고 리워드 파밍** — 계정당 `daily_cap`(기본 2회·5P) → N계정이면 N배 적립 → **열람권/(향후)수익화로 환산되면 실질 피해**. 광고 이중적립/캡우회(현수 H2·H3)와 곱해지면 규모 커짐. → [[project-reward-ad-server]]·[[project-ads-plan]]
2. **리뷰 무결성(가장 아픔)** — 한 근무지에 **다계정 소켓퍼펫**으로 다수 리뷰 → 별점·추천율 조작, "한 학기 1리뷰" 우회. **리뷰 신뢰가 제품의 핵심**이라 여기가 제일 치명적.
3. **탈퇴 쿨다운 자체** — 사실 부차적. 어뷰저는 애초에 탈퇴 안 하고 여러 이메일로 만들면 됨.

## 방어 전략 — 완벽 차단은 불가 → **계층 방어 + "이득 없게"**

> 핵심 원칙: Sybil을 *막으려* 하지 말고 **계정 하나의 가치를 낮춰 "다계정이 안 남는" 경제**를 만든다. (완전 신원검증은 이메일론 불가)

### Tier 0 — 지금(싸고 효과 큼)
- **이메일 정규화(canonical)**: 신원·쿨다운 해시 전에 정규화 —
  - 항상 로컬파트 **`+` 이후 제거**
  - **구글 도메인(`gmail.com`·`googlemail.com`·구글 워크스페이스)만 `.`(dot) 제거**
  - ⚠️ 다른 도메인에서 dot는 유효 → 제거하면 **오탐(서로 다른 사람 병합)**. provider별 휴리스틱이라 **화이트리스트 방식**으로.
  - → V1·V2 차단. **V3·V4는 못 막음**(별도 레버 필요).
- **광고 경제 상한 확인/강화**: `daily_cap`을 낮게(**⚠️ 디버그값 `1000000` → 실서비스 `2`로 복구 확인** — [[project-reward-ad-server]]), `cooldown_minutes>0`, **포인트→열람권 환산비를 다계정 파밍이 수지 안 맞게** 설계.
- **리뷰 영향 상한 유지 + velocity 탐지**: "1계정·1근무지·1학기" 유지 + **동일 근무지에 신규 계정 리뷰가 단기 급증**하는 패턴 모니터링(수동이라도).

### Tier 1 — 여력 될 때
- **per-IP / 디바이스 rate limit** (Cloudflare/Supabase 대시보드) — 대량 계정 생성·파밍 **속도** 제한. 현수 보고서의 브루트포싱/DoS 대시보드 작업과 **같은 레버라 묶어서**.
- **학교 소속 검증(현수 M3)** — 이메일 도메인 ↔ 선택 `university_id` 일치 강제 → 최소한 "임의 학교 주장" 차단(V4·V5의 리뷰 신뢰 훼손 완화).
- **캐치올/일회용 도메인 의심 처리** — 탐지가 어려워 후순위(MX 조회·의심목록 등).

### Tier 2 — 남용이 실제로 관측되면(무거움)
- **휴대폰 인증**(1폰 ≈ 1인, 이메일보다 배가 훨씬 어려움) — SMS 비용 + 가입 문턱↑. (VOIP/가상번호로 완전하진 않음)
- **학교 SSO / 학번 검증**(가능하면) — 진짜 "이 학생 맞음" 앵커.

## 권고 (MVP 단계)

1. **Tier 0만 우선** — 비용 대비 효과 최고: ① 이메일 정규화 ② 광고 경제 상한(특히 `daily_cap=2` 복구) ③ 리뷰 velocity 관찰.
2. Tier 1 rate limit은 **현수 보고서(브루트포싱/DoS) 대시보드 작업 때 같이**.
3. **휴대폰/SSO는 남용 신호 뜨기 전엔 과함** — 문턱만 높아짐. "광고 파밍/리뷰 조작이 실제 관측되면 도입"을 트리거로 잡아두고 대기.

> 요지: 이메일 기반으로는 Sybil을 **원천 차단할 수 없다**(V3·V4). 그러니 **계정 하나를 저가치화(광고 경제 상한·리뷰 영향 제한) + 정규화 + 속도 제한**의 계층 방어로 가고, 강한 신원(휴대폰/SSO)은 실제 남용을 트리거로 남겨둔다.
