# 리뷰 작성 — 입학연도 제약 삭제 설계

- 날짜: 2026-07-26 · 담당: 배경록
- 상태: 확정
- 관련: `web/src/pages/ReviewForm.jsx` · `web/src/lib/semesters.js` · `20260725120000_enforce_national_review_semesters.sql`(국가근로 학기 제한 — 이번 변경과 독립)

---

## 1. 목표

리뷰 작성 시 걸려 있던 **"근무 연도는 내 입학연도 이후여야 한다"** 는 제약을 없앤다.
근무 연도 선택지는 입학연도와 무관하게 **올해부터 3년 전까지 4개(롤링)** 로 고정한다.

**왜:** 편입·재입학·입학연도 오입력 등으로 실제 근무 이력과 입학연도가 어긋나면 리뷰를 **아예 못 쓴다.** 반대로 이 제약이 지켜주는 것은 없다 — 서버는 입학연도를 검사하지 않으므로(§2) 데이터 무결성 보장이 아니라 **실효 없는 UI 제약**이다.

**왜 하필 4개(올해~3년 전):** 근무 리뷰는 오래될수록 정보 가치가 떨어진다(담당자·업무 내용이 바뀜). 롤링이라 목록 길이가 해마다 늘지 않는다.

> **정책 경계:** 4년 범위는 리뷰 폼의 **UX 정책**이다. RPC 직접 호출까지 막는
> 서버 데이터 무결성 제약은 아니다. 이번 변경은 정상 UI의 선택 범위를 정리하는
> 프론트 변경이며, 서버 강제는 범위 밖이다.

**서버는 입학연도를 검사하지 않는다(확인함).** `write_review_with_points` / `update_review_with_points`(최신본 = `20260725120000_enforce_national_review_semesters.sql`)에 `admission_year` 참조가 없다.

있는 연도를 제한하지만, RPC 직접 호출을 보안 경계로 차단하지는 않는다(§1 정책 경계).

회원가입·프로필 수정의 **입학연도 입력 필드는 그대로 둔다**(수집은 계속). 없어지는 것은 "리뷰 작성 연도를 입학연도로 제한하는 로직"뿐이다.

## 3. 설계

### 3.1 `lib/semesters.js` — 순수함수 추가

```js
export const REVIEW_YEAR_SPAN = 4   // 올해 포함 4개 = 올해 ~ 3년 전

// 근무 연도 선택지(최신순). 입학연도와 무관.
export function reviewFormYearOptions({ now, include = null })
```

- 반환: `[2026, 2025, 2024, 2023]` (내림차순)
- `include`가 기본 범위보다 **오래된 유효한 과거 정수 연도**면 목록에 병합 후 재정렬.
- `include`가 `null`이거나 이미 범위 안이면 무시(중복 없음).
- 미래 연도·비정수·`NaN`은 무시한다. 레거시 수정 예외는 오래된 과거 리뷰에만 허용한다.
- `lib` 계약 준수 — 의존성 0, DOM 금지, `now` 주입으로 테스트 가능.

### 3.2 `ReviewForm.jsx`

```js
const yearOptions = reviewFormYearOptions({ now, include: originalWorkYear })
```

- **`originalWorkYear`** — 수정 모드에서 `fetchMyReviewById`로 불러온 `review.work_year`를 한 번만 담는 state.
  ⚠️ **현재 선택값(`workYear`)을 `include`로 쓰면 안 된다.** 2020년 리뷰를 열어 2025로 바꾸는 순간 2020이 목록에서 사라져 **되돌아갈 수 없다.**
- 여기서 "한 번"은 컴포넌트 생애 전체가 아니라 **현재 `reviewId`로 불러온 리뷰마다
  한 번**이다. `reviewId`/`worksiteId`가 바뀌거나 신규 작성으로 전환되면 이전
  `originalWorkYear`를 초기화해 예외 연도가 다른 폼으로 새지 않게 한다.
- `admissionYear` state와 `setAdmissionYear`, 그리고 §2의 가드 2개를 제거한다.
- `yearOptions`는 `useMemo`로 계산한다. 수정 데이터를 불러온 뒤 원래 연도가 계산된
  옵션에 없으면(미래 연도·비정상 값) `workYear`를 올해로 정규화한다.
- 드롭다운 변경과 제출 직전에도 "선택 연도가 옵션 목록에 없으면 올해로" 검증한다.
  오래된 원래 연도는 `include`로 옵션에 있으므로 그대로 저장하거나 다른 연도로
  바꿨다가 되돌아갈 수 있다.
- `reviewFormSemesterOptions`는 **그대로 둔다** — 연도만 받으므로 영향 없음. 과거 연도는 4학기 전부, 올해는 현재 학기까지만 노출하는 기존 동작이 유지된다.

### 3.3 죽은 코드 삭제

`availableSemesters`와 함께 이 함수만 쓰던 `currentYearSemester`·`semesterKey`, 그리고
`semesters.test.js`의 해당 `describe` 블록·옛 import를 삭제한다. 데이터 계층의
미사용 `fetchWrittenSemesters`도 같은 옛 흐름의 잔재이므로 삭제하고
`data/README.md` 설명을 갱신한다.

## 4. 엣지케이스

| 상황 | 동작 |
|---|---|
| 입학연도 2026인 사용자가 2023년 근무 리뷰 작성 | **허용** (이 변경의 목적) |
| 2020년 근무 리뷰(구 규칙으로 작성됨) 수정 | `include`로 2020이 목록에 남음 → 값 안 튐. 저장도 서버 무검사라 통과 |
| 인증 프로필 객체에 `admission_year`가 없음 | 이제 리뷰 작성 가능(폼 차단 없음). DB 컬럼은 `NOT NULL`이라 정상 계정 행 자체가 null인 상황은 없음 |
| 미래 연도 | `include`로도 병합하지 않음 + 로딩/변경/제출 검증이 올해로 되돌림 |
| 수정 리뷰 A → 수정 리뷰 B 또는 신규 작성으로 라우트 전환 | A의 `originalWorkYear`를 초기화해 B/신규 폼 옵션에 예외 연도가 남지 않음 |
| 국가근로 학기 제한(`semester`/`vacation`) | **무관** — 연도가 아니라 학기 필터라 그대로 동작 |
| 학기당 1리뷰 unique 제약 | 무관 — 연도 범위가 넓어져도 `(user, year, semester)` 중복은 서버가 그대로 막음 |

## 5. 테스트

**자동** (`web/src/lib/semesters.test.js`) — `reviewFormYearOptions`:
- 길이 4 · 내림차순 · 올해가 첫 원소
- `include`가 범위 밖(2020) → 목록 끝에 병합, 정렬 유지
- `include`가 범위 안(2024) → 중복 추가되지 않음
- `include: null` → 기본 4개 그대로
- `include`가 미래 연도·비정수·`NaN` → 기본 4개 그대로

**수동:**
1. 신규 작성 폼에서 연도 드롭다운이 4개인지
2. 입학연도보다 이전 연도(예: 2023)를 골라 저장되는지
3. 기존 리뷰 수정 진입 시 원래 연도가 유지되는지
4. 오래된 리뷰에서 범위 안 연도로 바꾼 뒤 원래 연도로 되돌아갈 수 있는지
5. 수정 리뷰 간 이동 또는 수정→신규 전환 시 이전 예외 연도가 남지 않는지
6. 인증 프로필 객체에 입학연도 필드가 없어도 폼이 열리는지(mock으로 확인)

**"프로필 수정 게이트: 비밀번호를 잊은 경우"** 는 이번 브랜치에서 제외한다(2026-07-26 결정). 이미 확정된 설계라 재논의 없이 그대로 쓰기 위해 기록만 남긴다.

- 잠금 화면([`MyPage.jsx:198-217`](../../../web/src/pages/MyPage.jsx#L198-L217))의 "확인" 버튼 **아래**에 `비밀번호를 잊으셨나요?` 링크 → 세션 이메일로 재설정 메일 발송. `data/authQueries.js`에 `sendPasswordResetToCurrentUser()`를 추가해 페이지가 이메일을 직접 다루지 않게 한다.
- **비밀번호 입력 폼은 남겨둔다** — 비번이 기억나면 바로 통과할 수 있게, 상태 분기도 줄일 겸.
- 발송 후 안내 문구 + 재발송, **쿨다운 60초**(Supabase의 동일 메일 최소 발송 간격과 일치). `useResendCooldown` 공용 훅으로 빼서 [`Login.jsx:120-129`](../../../web/src/pages/Login.jsx#L120-L129)의 재발송에도 같이 적용한다.
  → `Login.jsx`는 인증 담당(현수) 영역과 겹치므로 **착수 전 디스코드 공유 필요.**
- ❌ **폐기된 안:** 링크를 누르면 곧장 `/reset-password`로 보내기 — 비밀번호를 모르는 사람이 로그인된 기기에서 비번을 바꿔 게이트를 통과할 수 있어 **게이트가 무력화**된다. 메일 경유는 메일함 접근(=이메일 소유 증명)을 요구하므로 게이트의 의미가 유지된다.
- ❌ **폐기된 안:** 발송 후 링크 영구 비활성 — 메일이 지연되거나 스팸함에 들어가면 사용자가 그 화면에서 막힌다.
