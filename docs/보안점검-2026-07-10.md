# 근로고래 보안 점검 보고서

- 날짜: 2026-07-10
- 대상: `honeyjang/web` (React+Vite SPA · Supabase 직접 통신)
- 방식: 6개 영역 병렬 검토(브루트포싱·악성트래픽/DoS·해외IP/엣지·RLS/RPC 권한·포인트 경제·클라 시크릿/입력) + 각 항목 반증 검증
- 요청 배경: 로그인 브루트포싱, 악성 트래픽 급증, 아무 도메인 무차별 스캔, 해외 아이피 차단

## 요약

구조상 좋은 소식부터: **RLS·컬럼 권한이 대체로 잘 잡혀 있다.** 특권 컬럼(`point_balance`·`pass_balances`·`is_admin`)은 클라가 못 쓰게 막혀 있고, 자체 bcrypt 로그인 같은 옛 무제한 인증 경로는 컷오버에서 깔끔히 제거됐다. anon 키만 프론트에 노출되고 service_role 키·`.env`는 커밋 안 됐다. 리뷰 텍스트는 React 기본 이스케이프로 렌더돼 저장형 XSS도 없다.

문제는 세 가지 **실제로 악용 가능한** 구멍과, 요청하신 세 걱정거리에 대한 현실적 답이다.

**지금 고쳐야 하는 것 (High)**
1. **`postings` 표의 연락처 PII가 anon에게 전부 열려 있음** — 클라는 `contact_name`만 읽지만 RLS 정책은 모든 컬럼을 열어둠. anon 키로 전화번호·이메일·`raw_text`까지 대량 수집 가능.
2. **광고 보상 이중 적립 레이스** (`claim_ad_reward`) — 같은 토큰으로 동시 요청 시 포인트 N배 적립.
3. **광고 일일 한도(daily_cap) 우회** — 동시 요청으로 하루 한도를 넘겨 포인트 파밍.

**요청 3대 걱정거리에 대한 답**
- **로그인 브루트포싱**: 코드 차원엔 락아웃·캡차·백오프가 없다. 다만 실제 rate limit·캡차는 Supabase **클라우드 대시보드** 설정이라 이 저장소만으로는 프로덕션 상태를 증명할 수 없다 → 대시보드에서 확인·강화가 핵심. 저장소에서 바로 손댈 부분은 **이메일 존재 확인 오라클**과 **약한 비밀번호 정책**.
- **악성 트래픽/DoS**: 가장 현실적인 증폭 벡터는 **검색 RPC**(`search_worksite_cards`)다. 매 호출마다 리뷰·공고 전체를 집계하고 앞와일드카드 ILIKE로 풀스캔 → 인증 사용자가 루프 돌리면 CPU·커넥션 고갈. 일반적인 무제한 요청 방어는 CDN/WAF 몫.
- **해외 IP 차단**: 정적 사이트(grgr.kr, Cloudflare Pages)는 지오 차단 가능. 하지만 **진짜 공격면인 Supabase API(`*.supabase.co`)는 이 저장소로는 지오 차단 불가** — 별도 도메인이라 Cloudflare 규칙이 안 닿는다. 무차별 도메인 스캔도 정적 호스트는 WAF로 막지만 데이터 평면은 Supabase 플랫폼 방어에 의존.

## High — 우선 조치

### H1. `postings` 연락처 PII가 anon에게 전량 노출
- 위치: RLS 정책 `20260624025109_auth_rls_cutover.sql:427` · 컬럼 `20260609000000_baseline.sql:112-115`
- 사실: 정책이 `create policy postings_read on postings for select to anon, authenticated using (true)` — **컬럼 제한 없음**. 표에는 `contact_phone`, `contact_email`, `raw_text` 등이 있고, 클라(`worksiteQueries.js:15-18`)는 일부러 `contact_name`만 골라 읽는다(= 나머지는 공개 의도 아님).
- 영향: 누구든 anon 키로 `GET /rest/v1/postings?select=contact_name,contact_phone,contact_email,raw_text` 를 던지면 채용 담당자 연락처를 페이지네이션으로 통째로 긁어갈 수 있다. `max_rows=1000`이 한 번 응답만 제한할 뿐 반복 수집을 막지 못함. **요청하신 "무차별 스캔"과 직결되는 실제 PII 유출.**
- 조치: 표 전체 SELECT를 anon에 주지 말 것. 이미 쓰는 users 컬럼 화이트리스트 패턴을 그대로 적용 —
  ```sql
  revoke select on public.postings from anon, authenticated;
  grant select (id, worksite_id, source_url, job_category, preferred_track,
    preferred_college, preferred_dept, recruit_count, min_grade, eligible_degree,
    eligible_status, job_description, preference_notes, extra_notes, hourly_wage,
    work_period_text, work_duration_type, work_time_text, recruitment_period_text,
    contact_name, is_active, created_at)
    on public.postings to anon, authenticated;
  ```
  또는 안전 컬럼만 반환하는 SECURITY DEFINER 뷰/RPC로 감싸고 넓은 정책은 제거.
- ✅ **2026-07-13 조치**: 마이그레이션 `20260713144538_postings_pii_column_whitelist.sql`(detail_choi_3) — 위 화이트리스트 GRANT 그대로. 단 contact_phone/email은 20260619에 이미 컬럼 drop돼 목록에서 제외됐고, 남은 위험이던 `raw_text`가 차단 대상. **2026-07-14 push 완료 — anon `?select=raw_text` 요청이 permission denied로 차단됨을 실서버에서 확인.**

### H2. 광고 보상 이중 적립 레이스 (`claim_ad_reward`)
- 위치: `20260624170000_reward_ad_server.sql:87-100`
- 사실: `select ... where token=... and claimed_at is null` 에 `for update`가 없고, 이후 `update ad_views set claimed_at=now() where id=v_view.id` 에 **`and claimed_at is null` 가드가 없다.** READ COMMITTED에서 같은 토큰 동시 호출 2건이 모두 SELECT를 통과 → 둘 다 포인트 지급. `points(ad_view_id)` 유니크 제약도 없어 중복 insert가 막히지 않음.
- 영향: 정상 발급된 토큰 1개로 동시 요청 N개를 쏘면 1회 시청에 대해 `reward_points × N` 적립. 광고 경제 한도를 무력화.
- 조치: 행 잠금 + 조건부 UPDATE로 원자화 —
  ```sql
  select * into v_view from ad_views
    where token=p_token and user_id=v_uid and claimed_at is null for update;
  -- ...검증 후...
  update ad_views set claimed_at=now() where id=v_view.id and claimed_at is null;
  -- GET DIAGNOSTICS row_count=1 일 때만 적립, 아니면 INVALID_TOKEN
  ```
  방어선으로 `create unique index on points(ad_view_id) where ad_view_id is not null` 추가.
- ✅ **2026-07-14 조치**: 마이그레이션 `20260713164934_fix_ad_reward_race_h2_h3.sql`(detail_choi_3) — ad_views 행 `for update` + 조건부 UPDATE(`row_count` 확인) + `points(ad_view_id)` 부분 유니크 인덱스(기존 중복 행은 링크만 해제). **push 대기.**

### H3. 광고 일일 한도(daily_cap) 동시성 우회
- 위치: `20260624170000_reward_ad_server.sql:60-98`
- 사실: 한도 검사가 `select count(*) ... where claimed_at is not null and today` 후 비교(count-then-act)인데 사용자 행/뷰 집합을 아무것도 잠그지 않는다. `start_ad_view`를 여러 번 먼저 불러 유효 토큰 여러 개를 확보한 뒤 `claim_ad_reward`를 동시에 쏘면 모두 `v_today < cap`으로 읽혀 전부 성공.
- 영향: 하루 한도(기본 2)를 넘겨 포인트 파밍. H2와 겹치면 파밍 규모가 커짐.
- 조치: `claim_ad_reward` 시작에서 `select ... from users where id=v_uid for update`로 사용자별 직렬화 후 락 안에서 재집계, 또는 `daily_ad_claims(user_id, claim_date, count)` 원자 카운터(`count=count+1 where count<cap` + row_count 확인)로 강제.
- ✅ **2026-07-14 조치**: 같은 마이그레이션(`20260713164934`) — claim 시작에서 `users` 행 잠금(사용자별 직렬화, 잠금 순서 users→ad_views) 후 락 안에서 cap 재집계. `start_ad_view`의 cap 검사는 사전 안내용으로 유지(적립은 claim에서만 발생). **push 대기.**

## Medium

### M1. 검색 RPC 컴퓨트 증폭 (악성 트래픽의 핵심 벡터)
- 위치: `search_worksite_cards` (현행 정의 `20260708110000_region_filter_national_only.sql`) · `search_worksite_suggestions` (`20260627065818`)
- 사실: p_query/필터와 무관하게 매 호출 `reviews`·`postings` 전체를 집계(CTE)하고, 이름 매칭은 `ilike '%'||p_query||'%'`(앞와일드카드 → 인덱스 못 씀, 순차 스캔). 둘 다 `authenticated`에 grant, `statement_timeout`·인덱스·서버측 `p_limit` 상한 없음.
- 영향: 인증 사용자(가입 문턱 낮음)가 루프를 돌리면 각 호출이 CPU를 물고 커넥션 풀을 고갈 → 서비스 전체 저하. "싼 요청 → 비싼 쿼리" 증폭.
- 조치: (1) 집계를 요약 테이블/머티리얼라이즈드 뷰로 사전 계산, (2) `pg_trgm` GIN 인덱스 + 트라이그램/접두 매칭 또는 서버측 최소 쿼리 길이, (3) 함수 내 `p_limit`/`p_offset` 상한, (4) `authenticated` 역할에 `statement_timeout` 설정(폭주 쿼리 강제 종료), (5) 서제안 클라 디바운스 유지.
- ✅ **2026-07-14 부분 조치(3·4 + 최소길이)**: 마이그레이션 `20260713172824_search_rpc_limits_and_timeout.sql`(detail_choi_3) — cards `limit≤50`(클라 perPage 최대 50)·`offset≤10000`·null 방어(`limit null`=전체 반환 차단), suggestions `limit≤20`+최소 쿼리 길이 2(클라 MIN_QUERY_LEN=2와 일치, 미만은 빈 결과), `anon`/`authenticated` `statement_timeout='3s'`. **push 대기.**
  - ⏳ 미조치(후속): (1) 사전집계·(2) pg_trgm — 호출당 전체 집계+순차 스캔 비용 자체는 그대로라 "정상 크기 호출 반복" 공격엔 여전히 취약. 리뷰 수천 건↑ 또는 검색 체감 지연 시 (1)→(2) 순으로 도입. 반복 호출 자체는 대시보드 API rate limit 영역.
  - ⚠️ 운영 주의: statement_timeout은 해당 역할의 **모든** 쿼리에 걸림 — 이후 느린 정상 기능이 생기면 이 3s부터 의심.

### M2. Supabase 데이터 평면은 지오 차단 불가 (해외 IP 요청의 현실)
- 위치: `web/src/supabase.js:3-8` · `README_supabase.md:28` (`*.supabase.co`)
- 사실: 브라우저가 `*.supabase.co`(Supabase 자체 도메인)로 직접 통신. grgr.kr에 건 Cloudflare 지오/WAF 규칙은 여기에 **안 닿는다.** 즉 완벽히 KR 지오게이트를 걸어도 로그인/RPC/읽기 같은 실제 공격면은 전 세계에서 도달 가능.
- 조치: "데이터 평면 지오 차단은 이 저장소로 불가"임을 팀에 명확히 공유. 현실적 대안 순서 — (1) Supabase Auth 내장 per-IP rate limit + 캡차(대시보드)로 완화, (2) 하드 게이트가 꼭 필요하면 `api.grgr.kr` 앞에 Cloudflare Worker 프록시(작업량 큼, 보통 MVP엔 과함), (3) `db.network_restrictions`는 **직접 Postgres(5432) 연결만** 제한 — 앱 HTTP API엔 무관하니 앱 트래픽 차단용으로 오해 금지.

### M3. 가입 학교 제한 완화 + 학교 소속 미검증
- 위치: `20260626152144_relax_signup_domain.sql:16-21` · `create_profile` (`20260626163424_otp_signup.sql:17-63`)
- 사실: 트리거가 이메일 도메인이 `.ac.kr`로 끝나는지 + `university_id` 존재 여부만 본다. **이메일 도메인과 선택한 `university_id`의 실제 학교가 일치하는지 검증하지 않음.** 단과대/학과 이름이 안 맞으면 조용히 `order by id limit 1`로 첫 값 대입.
- 영향: 아무 `*.ac.kr` 메일이면 고려대 등 임의 학교 소속을 주장하며 가입 가능 → 리뷰에 표시되는 "학교 소속" 신뢰가 실제 이메일과 무관해짐. 인증 사용자 풀이 넓어져 포인트/리뷰/신고 남용 여지도 커짐.
- 조치: 전 `.ac.kr` 허용이 의도면 문서화하고, 최소한 `handle_new_user`/`create_profile`에서 선택 `university_id`의 `email_domain`이 확인된 이메일 도메인과 일치하는지 검증. 특정 학교만 허용할 거면 제거된 `signup_enabled`/도메인 매칭 복원.

### M4. 이메일 가입 여부 오라클 (계정 열거)
- 위치: `20260626153426_email_registered_check.sql:9-23`
- 사실: `email_registered(p_email)`가 anon에 grant, `auth.users`를 조회해 가입 여부 boolean 반환. 파일 주석도 "enumeration 트레이드오프 … 완화책(rate limit/캡차)은 후속"이라 명시. PostgREST RPC라 Supabase Auth의 rate limit이 **적용 안 됨** → 무제한 열거.
- 영향: 누구든 anon 키로 임의 이메일의 가입 여부를 대량 확인 → 표적 브루트포싱·피싱 리스트·회원 여부 프라이버시 유출. (실제 비밀번호 추측 단계는 GoTrue가 별도로 throttle하지만, 열거 자체가 무제한이라 표적화를 돕는다.)
- 조치: 사전검사를 없애고 로그인 실패를 일반 메시지로 처리하는 게 가장 깔끔(로그인 화면이 이미 실패를 단일 메시지로 합침). 유지해야 하면 엣지/WAF per-IP throttle 또는 캡차 뒤로 이동.

## Low / Info (요약)

**Low**
- **로그인 방어는 대시보드 의존**: 코드엔 락아웃/캡차/백오프 없음. `config.toml`은 로컬 전용이라 프로덕션 증명 불가 → 대시보드에서 hCaptcha/Turnstile + 유출 비밀번호(HIBP) 보호 켜고, 켠 뒤 `signIn/signUp/resend`에 `options.captchaToken` 전달 필요(현재 클라 미지원이라 켜기만 하면 흐름이 깨짐).
- **약한 비밀번호 정책**: `minimum_password_length=6`, 복잡도 없음(대시보드 값). 클라 8자 체크는 UI뿐이라 직접 RPC로 우회 가능 → 대시보드에서 10자+·복잡도·HIBP 권장. (참고: 클라 라벨 "최소 8자리" vs 서버 6자 불일치.)
- **`report_review` 신고 스팸**: 존재/소유 검사 없이 임의 review_id로 무제한 신고 insert 가능(모더레이션 큐 오염). `p_reason` 검증·존재 확인·`unique(reporter_id, review_id)` 필요.
- **`increment_worksite_view` 무제한/무중복**: 인증 사용자가 루프로 조회수 임의 조작(홈 "많이 찾아본 순" 왜곡) + 핫 행 UPDATE 반복. `(user, worksite, day)` 유니크로 중복 방지.
- **읽기 쿼리 LIMIT 누락**: `fetchHomePostings`(학교 분기)·`list_worksite_reviews`·마이페이지 목록에 `.limit()` 없음(에그레스/CPU 증폭, 데이터 유출은 아님). 페이지네이션 추가.
- **포인트 지갑 read-modify-write에 락 없음**: `update/delete_review_with_points`가 `for update` 없이 잔액 확인 → UPDATE. `point_balance>=0` CHECK가 최종 방어라 잔액이 음수로 커밋되진 않지만, 에러 처리가 `purchase_pass`(안전 패턴)와 불일치. 가드를 UPDATE WHERE로 접어 통일.
- **광고 보상 봇 파밍**: `min_view_seconds`는 고정 대기라 스크립트가 그냥 기다렸다 청구 가능(설계 한계). daily_cap 낮게 유지 + `cooldown_minutes>0` + per-IP 제한.
- **`window.open` 스킴 미검증**: `AdModal`의 `target_url`, `InfoCard`의 `source_url`(후자는 `noopener` 누락 → 리버스 탭내빙). 오늘은 두 값 모두 관리자/service_role만 쓸 수 있어 악용 경로는 없지만, `new URL()`로 `http(s):` 검증 + `noopener,noreferrer` 통일 권장.

**Info**
- 정적 호스트(grgr.kr)에 지오/WAF/rate-limit 규칙이 저장소에 없음 → Cloudflare 대시보드에서 `ip.geoip.country ne "KR"` Managed Challenge + OWASP 매니지드 룰셋(+ `/wp-admin`·`.env` 스캔 차단) + rate limit 설정 권장. `_redirects`가 모든 경로를 200 index.html로 넘겨 스캐너에 항상 풀 페이지 응답(비밀 유출은 없음).
- SECURITY DEFINER 검색/집계 RPC 3개(`get_worksite_score_cards`·`search_worksite_cards`·`search_worksite_suggestions`)에 `set search_path` 미고정 — 오늘은 anon/authenticated가 스키마 생성 권한이 없어 악용 불가하나 린터 경고이자 컨벤션 위반. `set search_path = public` 추가 권장.

- 익명 리뷰가 `work_year`는 노출(재식별 보조, 직접 식별자 아님). 강한 익명성 원하면 null 처리.
- `db.network_restrictions` allow-all은 로컬 스캐폴드 기본값(로컬 전용). 클라우드 대시보드에서 직접 DB 접근 IP만 화이트리스트 권장(앱 트래픽엔 무영향).

## 권장 처리 순서

1. **H1** — anon `postings` 컬럼 권한 축소 (실제 PII 유출, 마이그레이션 한 개로 해결).
2. **H2·H3** — 광고 보상 RPC에 `for update` + 조건부 UPDATE + 유니크 제약 (포인트 경제 무결성).
3. **대시보드 점검(로그인 걱정거리)** — 캡차(hCaptcha/Turnstile) on + HIBP 유출 비밀번호 보호 on + per-IP rate limit 값 확인 + 비밀번호 정책 10자+/복잡도. 캡차 켜면 클라 `captchaToken` 배선 필요.
4. **M4** — 이메일 열거 오라클 제거 또는 캡차/throttle 뒤로.
5. **엣지(해외IP·스캔 걱정거리)** — Cloudflare grgr.kr에 KR 지오 Managed Challenge + WAF 매니지드 룰셋 + rate limit. **단, 데이터 평면은 못 막음**을 전제로.
6. **M1** — 검색 RPC 인덱스/타임아웃/상한.
7. **M3** — 학교 소속 검증 또는 정책 문서화.
8. 나머지 Low/Info는 후속 하드닝 티켓으로.

> 참고: `config.toml`은 **로컬 개발 전용**이다. 로그인 rate limit·캡차·이메일 한도·비밀번호 정책·네트워크 제한의 실제 프로덕션 값은 **Supabase 클라우드 대시보드**에 있으며 이 저장소로는 확인·증명할 수 없다. 위 로그인/이메일 관련 항목은 반드시 대시보드에서 실제 값을 확인할 것.
