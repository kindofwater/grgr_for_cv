# `web/supabase/` — Supabase CLI (DB 정본)

Supabase **CLI 설정 + 마이그레이션**을 두는 곳. 앞으로 DB 스키마·RPC·시드의 **정본(source of truth)** 이며,
여기 SQL을 `supabase db push`로 실제 DB에 반영한다. (예전: `DB/` 폴더 + SQL 에디터 수동 복붙 → 레거시)

> ⚠️ **baseline 방식(Docker 없이):** `db pull`은 Docker가 필요해서 쓰지 않았다. 대신 검증된 `docs/db-schema.md` + `DB/` RPC를 손으로 옮겨 `migrations/20260609000000_baseline.sql`로 만들었고, live엔 이미 존재하므로 `migration repair --status applied`로 "적용됨"만 기록한다. 이후 변경부터 `migration new` + `db push`.

"내가 만든 것만 나간다"고 가정하지 말고 **push 전에 `npx supabase migration list`로 대기 목록부터 볼 것**(팀 공유 DB라 남의 미적용분이 쌓여 있을 수 있다). 📌 **첫 실행은 2026-07-17 13:00 KST** — push 시점(22:50 KST)엔 그날 13:00이 이미 지나 `cron.job_run_details`가 0행인 게 정상이었다. 이후 `status='succeeded'`만 확인하면 된다(`return_message`가 `DELETE 0`이어도 정상 — 지울 만료 해시가 없는 것과 실패는 다르다). `withdrawn_emails` 만료 해시 **자동 파기**: `pg_cron` 확장 활성(**이 프로젝트 첫 사용** — `cron` 스키마 생성) + 일일 잡 `purge-withdrawn-emails`(매일 04:00 UTC=13:00 KST)가 `withdrawn_at <= now() - 30 days` 삭제. **왜**: 기존 청소는 `delete_account()` 안의 **기회적** 삭제뿐이라 탈퇴가 뜸하면 해시가 30일을 넘겨 남고, 개인정보처리방침 제4조("회원 탈퇴 후 30일"·"이메일 해시값만 30일간 보관")와 어긋남 → 실제 파기를 스케줄로 보장. ⚠️ **`handle_new_user`의 `withdrawn_at > now() - 30 days` 필터는 빼지 말 것** — 필터=정책 집행(정확성)/cron=보유기간 파기(컴플라이언스)로 역할이 다름: cron이 실패·지연·미적용이면 조용히 부당 차단되고, cron은 하루 1회라 필터를 빼면 실질 쿨다운이 "30일+최대 24h"가 되어 방침과 어긋남. `delete_account()`의 기회적 삭제도 이중 안전망으로 유지. `cron.schedule`은 job 이름 기준 upsert라 멱등(재push·reset 안전). 확인 `select * from cron.job;` / 이력 `select * from cron.job_run_details order by start_time desc limit 5;` / 해제 `select cron.unschedule('purge-withdrawn-emails');`. ⚠️ `create extension pg_cron`이 권한으로 막히면 Dashboard→Database→Extensions에서 켜고 `cron.schedule`만 실행. 담당 배경록.

## DB 바꿀 때 (워크플로우)
1. **변경 전 팀에 공유.**
2. `npx supabase migration new <주제>` → 생성된 파일에 SQL 작성. **맨 위에 헤더 2줄 필수:**
   ```sql
   -- 목적: <무엇을 왜 바꾸는지 한 줄>
   -- 날짜: YYYY-MM-DD · 담당: <이름>
   ```
3. **검증(선택):** Docker 있으면 `npx supabase start` → `npx supabase db reset`로 맨바닥 재구축 테스트. **Docker 없으면(현재 방식)** 두 번째 무료 프로젝트를 sandbox로 만들어 `db push`로 테스트.
4. **prod 반영:** `npx supabase db push` — **변경한 사람이 직접**(특히 RPC). push 전 디스코드에 한 마디.

## 국가근장 모집기간 반영(정기 운영 — 학기·방학마다)

국가근장은 KOSAF 일괄 모집이라 근무지별 마감 추측이 성립하지 않는다(**추측 금지**).
학기·방학 집중근로 **모집기간 공지가 확정될 때마다** 아래 템플릿으로 마이그레이션을 만들어 push한다.
이 UPDATE가 교외 6,647건의 낡은 `is_active`도 겸사겸사 해소한다(별도 백필 불필요 — spec `docs/superpowers/specs/2026-07-17-kupid-school-postings-design.md` §2).

> ⚠️ 방학(하계·동계)은 신청기간이 대체로 동일하지만 **1·2학기는 방학마다 기간이 다르다** —
> 규칙으로 계산할 수 없으므로 학교근장 캐스케이드(`recruit_until.py`) 같은 자동 추정을 쓰지 않고,
> 공지가 뜰 때마다 확정 날짜를 이 템플릿으로 **직접 입력**한다(estimated=false).

```sql
-- 목적: 국가근로 <2026-2학기|2026-동계방학> 모집기간 반영 — recruit_until 일괄 입력(확정값)
-- 날짜: YYYY-MM-DD · 담당: <이름>
update postings p
   set recruit_until = '<접수 마감일 YYYY-MM-DD>',
       recruit_until_at = '<접수 마감일 YYYY-MM-DD HH24:MI:SS+09>'::timestamptz,
       recruit_until_estimated = false,
       is_active = (now() < '<접수 마감일 YYYY-MM-DD HH24:MI:SS+09>'::timestamptz),
       updated_at = now()
  from worksites w
 where w.id = p.worksite_id and w.type = 'national' and p.deleted_at is null;
```

`recruit_until_at`은 정확한 시각이 공지된 경우에만 넣고 반드시 `+09`를 명시한다. 값이 있으면
검색·홈·상세 모두 이 시각을 우선하며, 없으면 기존 `recruit_until` 날짜 판정으로 폴백한다.
기간 미확정이라 실제 마이그레이션 파일은 확정 시점에 만든다.
